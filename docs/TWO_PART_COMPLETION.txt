Delivery boundaries and safeguards
- Two product parts do not mean skipping intermediate local tests or commits.
- Create each Nestwise PR only after its whole part is reviewable; report
  external prerequisites honestly, never mark an unavailable feature complete.
- CRM source changes MUST stay in its own repository and its own review PR.
  This necessary cross-repository companion is not a third product part.
- Preserve existing CRM working-tree changes. Build from an isolated clean
  checkout when modifying its code; never overwrite unrelated local work.
- Before CRM edits, record exact mutation paths and additive migration/rollback
  plan. Producer flag OFF; no production mutation/deployment or historical push.
- Snapshot staging before new migrations; test restore and restricted runtime.
- Workiz integration excluded. No new bank connections or paid OCR subscription
  assumed. Secrets remain in existing secret stores, never repository contents.
- Owner/accountant decisions still needed for accounting basis, inventory,
  mixed-use expenses, tax/tip treatment and annual form version.

Acceptance requires end-to-end data flow and failure recovery, not merely
screens or passing unit tests. Native JS export is not a signed device build.
