Statement periods and balance evidence — 2026-10-20

Part 1 implementation; not deployed to staging yet.

Open an archived original to enter its inclusive period, opening/closing USD
balances and account last four digits. An explicit confirmation saves a new
immutable revision. This is user-declared evidence, not bank-certified metadata.
The server verifies original bytes against SHA-256 and computes net movement,
expected closing balance, signed difference, out-of-period and ambiguous rows.
A mismatch can be saved for investigation but is visibly flagged. No journal
transaction is created or changed by saving a period.

Account overview compares the latest revision of each original for gaps,
overlaps, adjacent balance differences and inconsistent last four digits.
Transaction-free days do not establish missing coverage; declared periods do.
Overlapping originals remain visible and are not silently deduplicated.

API (existing authenticated account ACL and origin protection):
GET /v1/user/workspaces/{workspace}/accounts/{account}/statement-periods
  Latest revision per original, at most 100 originals per account.
GET /v1/user/workspaces/{workspace}/accounts/{account}/documents/{hash}/period
  Full immutable revision history for that original, newest first, max 100.
POST same document period path, JSON <= 4096 bytes:
  {id: UUID, expected: previous revision (0 for first), data: {
    from: YYYY-MM-DD, to: YYYY-MM-DD, opening_cents: signed integer string,
    closing_cents: signed integer string, last4: four digits, confirmed: true}}
  Server derives all checks. Exact command retries return the original UUID.
  Stale version or changed reuse of UUID returns 409. Invalid data returns 400.
  Unknown/inaccessible account returns 404. Original copy integrity failures
  remain unavailable; the API never trusts client-supplied calculated totals.
